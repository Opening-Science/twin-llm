### Added

- Rhythm benchmark on the Long-Term AF Database (#264), a database that played no part in the Dash et al. 2009 thresholds. `bun run rhythm-bench -- --ltafdb <dir> [--real-noise]` reads its 84 records (about 24 h each at 128 Hz, Open Data Commons Attribution License, read in place and never copied into the repository) with the same WFDB readers, windows, flag, record-level bootstrap and noise levels as `--afdb`. Beats come from the manually reviewed `.atr` beat annotations, which this database has and the MIT-BIH AF Database does not; AF is `(AFIB` and every other rhythm is not AF. `scripts/rhythm-bench/databases.ts` holds what differs between the two databases; records are read one after another and windows are appended in place, so 24 h records stay linear in time. `result.json` names the database (`real.databaseId`). Results in `docs/research/rhythm-bench-2026-10.md`, "Independent database": on 84 records the flag marks 95 % of AF windows (0.947 [0.921, 0.967]) at 84 % specificity (0.841 [0.773, 0.898]), overlapping the MIT-BIH AF Database (0.954 and 0.796); with the grid's beat-detection noise specificity falls to 0.30 at light and 0.03 at heavy, as it did on the MIT-BIH AF Database.
- Decline wording comparisons on the held-out S7h set (#274): `bun run eval -- --decline-wording w1|w2|w3` runs one of three decline lines (`scripts/evaluation/decline-wordings.ts`; W1 is the chat route's `DECLINE_RULE`) for that run only, records its id and sha256 in `meta.json` and names it in the report. The chat default is unchanged. The wordings and the rule for choosing between them are in `docs/research/eval-runs-2026-10.md`, "Choosing the decline wording on S7h". Results on S7h for qwen3:8b and qwen3:4b: good decline pairs summed over both models W1 8/16, W2 2/16, W3 10/16, with 4, 14 and 4 missed declines; W3 is recommended, by a margin of two pairs on one sample per line. One sample per line; no human review.

The General agent and the base model lose most lines to a refused chart call after the tool and to swapped or miscoded exposure and outcome. - `cohort_event_rates` (#293), the first audited tool that counts events across a cohort: how often one recorded condition follows another in one loaded synthetic cohort, with the heart-brain study's designs, `within` (the same people before and after their own exposure onset; crude exact and age-adjusted rate ratios) and `between` (4 age- and sex-matched people without the exposure). Closed `.strict()` input (cohort id, SNOMED enums for exposure and outcome, design, optional age floor), counts only (never a subject_ref or a person's date), two capped reads (50,000 subjects, 50,000 conditions), audited with the rows read, synthetic mode only, and coded refusals (`COHORT_NOT_SUPPORTED`, `DESIGN_NOT_SUPPORTED`, `COHORT_RECORD_CAP_EXCEEDED`; personal mode and unlisted cohorts are `SUBJECT_SCOPE_VIOLATION`). The study's pure functions (`poisson`, `cohort`, `within-person`, `matched`, `codes`, the verdict) moved from `scripts/heart-brain` to `packages/query-tools/event-rates/`, so the study and the tool share one definition. On all 100 batches' people with AF it gives the study's numbers: 26 strokes before AF onset and 272 after, age-adjusted 3.09 (2.07 to 4.63), within 0.01 with the warehouse's birth and death years only. New evaluation cohort `synthea-v4-1m-af`, every person with AF in the 1M batches (9,558), copied out by `bun run heart-brain:af-subset` and loaded into the eval database only. `/brain` lists the tool. 19 hb items (`evaluation/questions.hb.v1.json`, `bun run eval -- --set hb`) with a rule fixed before any model ran: verdicts on planted and unplanted relations, two leading questions, numbers, four refusals and four person-level declines, keyed by the tool (`bun run eval:answer-key:hb`), plus an exact verdict check (`bun run eval:hb-verdicts`). - Genome variants as a local-only chat tool (#307): `genome_variants({ dataset_id, variants })` looks up named variants in a VCF the person imported (#180), by rsID or a GRCh38 site written `chrN:pos`, at most 50 names a call. For each name it returns found or not and the records as the file wrote them (chrom, pos, ID, ref, alt, GT, the GT in bases, filter); not found is said not to mean the reference allele. No ranges, genes or scans. It comes with the genome tools under `permitGenomeRequest` (personal mode, Ollama on loopback) and asks the policy again on every call. Coded refusals for an unknown dataset (listing the person's VCFs), another kind of dataset, too many names, names it cannot read and more than 200 matching records. One `genome.variants` audit row per call with the number of names asked and found only. A thread where it ran stays on local models. The MCP server lists it and it always refuses there with `GENOME_NOT_PERMITTED`. New source `vcf-variants`; `/genome` lists the tool. Tests use genome-synth VCFs only.
- Import a genome VCF, local models only (#180): Customize · Data takes one person's VCF 4.x, plain or gzip (bgzip included), through the same review and Save flow as the other imports. The file is read as a stream (gzip inflated in 64 kB steps, text in 1 MB steps) and refused, not cut, past 500 MB of text or 200,000 variant records; a whole genome is over that cap. Only GRCh38 is read: the build comes from `##reference` and contig `assembly=` names, GRCh37 or hg19 is refused as `BUILD_MISMATCH`, another build as `BUILD_UNKNOWN`, and a file that names none is refused unless `GENOME_ASSUME_BUILD=GRCh38`, as in `docs/genome.md`. Per record the chromosome, position, ID, alleles, FILTER and the sample's GT are stored in the new `personal_variants` table (migration `20261030120000_personal_variants`, kind `vcf`, `genome_build` on the dataset); QUAL, INFO, other FORMAT fields and the sample name are not. Malformed, symbolic and reference-only records are reported by reason; several samples or none are refused. The review shows genotype counts and records per chromosome. Audit rows hold the kind, byte size and counts only, with no SHA-256 for a VCF. The imported-data chat tools never list a VCF; a model may read its rows only on this machine under `permitGenomeRequest`, and no such reader exists yet. Tested on `scripts/genome-synth` output and made-up lines only. See `docs/personal-data.md`, "Genome VCF".
