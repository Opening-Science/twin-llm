# Changelog

Notable changes to TwinLLM. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- Wearable tools (#133): `sleep_summary` (main sleep per night and averages), `hrv_trend` and `resting_hr_trend` (slope per day and week, and the last 7 days against the 28 before them) and `training_load` (workout minutes per day or week, Whoop strain, Oura calories, sport, and recent load compared with the previous four weeks). Every row names its source and sources are never pooled. Personal mode reads the turn's linked Oura, Whoop and Google Health snapshots; synthetic mode reads a synthetic subject's synthetic series. Refusals: `SOURCE_NOT_CONNECTED`, `NO_ROWS`, `MIXED_UNITS`, `WINDOW_TOO_SHORT`. They have their own source toggle, and `/sleep` uses `sleep_summary`. The synthetic wearable generator (v2) adds workouts without changing the daily series, and writes the evaluation cohort's series only for the throwaway eval databases (`--allow-eval-cohort`). Twelve eval items (four refusals) were appended; earlier items and key values are unchanged.
- `/trainer`, descriptive (#46): a daily check-in or weekly review of recovery or readiness, HRV, resting heart rate, sleep and workouts against the person's own previous four weeks, built on the wearable tools, with every number's source named and charts in the weekly review. It gives no training suggestion, no dose, no injury or illness prediction and no medical claim; its eval cases include refusals for advice and dose questions and for hosted providers. Local Ollama only. See `docs/skills.md`.
- `/twin` shows the digital twin in the chat (#168), as a card after the turns, without asking any model: it starts no turn and is never in a model's history. In synthetic mode it is the first synthetic subject the thread used (on the Demo body with their lab values), else the Demo body; in personal mode, Self. The card names the twin, reuses the Digital Twin page's viewer in a shorter view loaded only when opened, collapses to a chip or closes, and a second `/twin` reopens it. Its state is kept per thread in sessionStorage.
- Incognito chats (#169): a switch on the empty new chat opens `/?incognito=1`, a chat that is never saved and runs only on local models (Ollama on loopback). The conversation lives in the browser tab: no thread, turn or answer row, no thread history entry, no `/t/<id>` URL, no analytics event about it and no prompt or answer text in a log; a reload or a new chat discards it. `POST /api/chat/incognito` takes a closed body without a turn id, refuses any other model with `INCOGNITO_LOCAL_ONLY` before calling it, and runs the same skill, genome and data-mode rules, tools and stream as `/api/chat`. Tool reads are audited under a random session id per answer. The picker greys out models that are not local, a banner says what the mode means, and the prompt bar is dashed.
- Import your own data (#176) on Customize · Data: FHIR records (Bundle, resource or NDJSON), lab results as CSV and research tables (CSV/TSV), up to 50 MB. A review shows counts, dates, codes, units, rows that will not be stored and why, and a preview; nothing is stored before Save. Each import is a dataset you can rename or delete for good, stored in new `personal_*` tables (additive migration `20261027220000_personal_imports`), never the warehouse. Units are kept as written; lab names get a LOINC code only from an explicit table over the Anchor catalogue. Personal mode only, audited without values, and the data-mode policy keeps imported data off every hosted model. Apple Health (#178), wearable exports (#179), VCF (#180) and chat access (#181) come next. See `docs/personal-data.md`.
- Your own skills (#174): Customize · Skills has a form to make a skill (name, what it does, instructions, sources and tools, views, providers) with a live preview of what the palette will say. Held to the SKILL.md schema, stored per person in `user_skills` (migration `20261027210000_user_skills`), listed in the palette and search, runnable like a shipped skill and marked not evaluated; editable and deletable by its owner only.
- Customize page (#172): `/customize` with Skills (the shipped skills as cards: what each reads, may call and where it runs, with Try), Data (open datasets; imports follow) and Connectors, which moved here from `/connectors` (that address redirects with its query, so sign-in returns still land). The sidebar's Connectors item is now Customize.
- Search box (#167): Ctrl/⌘+K or Search in the sidebar finds your threads (by words and by meaning), pages, docs and `/` commands, with tabs, recents and actions. Meaning matches use local nomic-embed-text embeddings stored without text in the new `thread_search_embeddings` table (migration `20261027200000_thread_search_embeddings`); genome threads are found by title only and never embedded; each search is audited without its query. A command opens a new chat with it typed in.
- `bun run dev` checks that `node_modules` matches `package.json` first and runs `bun install` when a pull added or bumped a package (#163), so a new dependency no longer breaks every page with "Module not found". `bun run doctor` reports the same check.
- Sex, birth year and death year for synthetic subjects (#4): an additive, nullable migration on `subjects` (years only, never a full date; a CHECK keeps them null unless `is_synthetic`), filled at ingest from the Synthea Patient. Re-running `warehouse:ingest`, or `setup:local -- --reload-cohort`, fills them for cohorts ingested before. `range_position` now places a value against a sex- or age-specific Anchor v3 range, with the age stated as approximate (birth year only) and "depends on age" when the band changes within the reading's year. The Data page splits each cohort by sex and 10-year age band. Eval: Q-S1-16 now has a position and a `range_high` key value; Q-S1-25 (HDL, where sex decides the range) is new; the other 142 key values are unchanged.
- `conditions_timeline` and `medications_timeline` (#130): a synthetic subject's recorded conditions (span overlapping a window) and medication requests (authored in it), oldest first, with codes, dates, recorded statuses and counts; optional status and code filters; dosage only as the record's own text, labelled as recorded. Nothing matching is refused with `NO_ROWS` and the reason. Both belong to the Subjects and observations source; the system prompt says to relate dates as before or after, never as a cause, and to add no dose or advice. Six eval items (two refusals) were appended; earlier items and key values are unchanged.
- The warehouse stores Synthea conditions and medication requests (#127): new tables `conditions` and `medication_requests`, filled in the same bundle transaction as the observations, values as recorded (a medication coded through a Medication reference is resolved in the bundle; dosage is only the record's text). The cohort reload deletes them too, and setup marks an evaluation cohort ingested without them as stale; `bun run setup:local -- --reload-cohort` fixes it. The pinned cohort has 1,995 conditions and 3,615 medication requests.
- `convert_unit` (#120): exact, table-driven conversions for glucose, creatinine, HbA1c, total/LDL/HDL cholesterol, triglycerides and body temperature, each pair in both directions, with the formula and rounding rule in the result; any other pair is refused with `UNSUPPORTED_CONVERSION`. The system prompt says to convert only through the tool. One table (`packages/query-tools/unit-conversions.ts`) now feeds the tool, the number matcher and the hallucination scorer. Eval items may name their measures (`expect.measures`), and three convert_unit items (one refusal) were appended; earlier items and key values are unchanged. Training `unit_conversion` answers call the tool, or keep the stored unit for pairs it does not cover.
- Synthetic genomes (#106): `bun run genome:synth` writes a seeded VCF 4.2 (GRCh38, marked synthetic) and the Ark rsid-genotypes report for a synthetic subject, from a curated catalog of 92 public variant sites with sources and licences (`scripts/genome-synth/variants.tsv`). `bun run genome:ingest` writes released reports for a Synthea cohort to a gitignored JSONL, or with `--to-db` (`genome:ingest:db`) to `genome_reports` as rows flagged synthetic and tied to the warehouse subject, never to a user (a CHECK constraint allows exactly one owner). `training:conversations --genome` adds seven genome families with the chat's `genome_report` and `dna_ask` and a stand-in Carbon-X answer; off by default. See `docs/genome-synthetic.md`.
- Numbers in a finished answer that a tool call returned are quiet links (#111): pressing one opens the tool card that holds it and lists the rows and fields it came from. A number with no source stays plain. The evaluation report adds "Unsourced numbers" per model, counted with the same matcher; it is an extra metric and changes no pass, fail or human tally.
- An Outputs panel per thread (#37) lists every chart its answers show, newest first, with title, kind, model and time. A row scrolls to the chart in its answer and Enlarge draws it large in the panel; the panel collapses or closes and remembers that in this browser. Two new model tools, `list_views` and `open_view`, let "show that chart again" reopen the stored chart instead of querying again; both are audited, a synthetic request is not offered wearable charts, and a skill turn gets them only when its skill allows views. Views with no readings are listed dimmed with "No readings".
- Chart titles use plain dates (`Heart rate, 1 Jan 2016 – 31 Oct 2026`), never a raw timestamp, and `show_view` refuses a measure that is neither a LOINC code nor a known wearable key (`UNKNOWN_MEASURE`) instead of drawing an empty chart. Titles already stored keep their old form.
- The Body twin can walk: Walk and Idle in the 3D toolbar play a generic, computed walk cycle (in place) and a standing breath with sway on a BodyLoop scan's skeleton or on a rigged demo body. No motion-capture data; the lines beside the view say it is not this person's gait. Anatomy layers fade out while the body moves, and reduced motion or a body without a skeleton disables both, with the reason.
- `bun run anatomy:fetch` downloads the rigged demo bodies from the `anatomy-rigged-v1` release and checks their SHA-256 pins, on every platform and without Python; `setup:local` bakes them only when the download fails. The bake's lock now resolves on macOS (torch from PyPI there, from the CPU index on Linux and Windows), and a bake that misses its pin says whether the body differs or only its float encoding.
- `bun run setup:local` and `bun run doctor` mark an evaluation cohort that is not the pinned one `[stale]`; `bun run setup:local -- --reload-cohort` replaces that cohort's warehouse rows in one transaction. `bun run doctor` lists why the Data page could be empty (DATA_MODE, allowlist, synthetic subjects, rows).
- `bun run anatomy:bake-rigged` bakes the ANNY demo bodies with their skeleton and skin weights from the pinned `anny` Python package (via uv) and installs them only when they match their SHA-256 pins; the viewer prefers them over the static bodies.
- Training conversations ask in several styles with typos, varied dates and units, add no-data families (measures no tool can read, vendor keys, periods outside the record, odd refs, similar-sounding measures) and unit families (mixed units, conversions), use the chat's twelve tools and system prompt, and write stats. `training:split` holds out whole template groups and LOINC codes for validation.
- Skill format: `skills/<name>/SKILL.md` lists the tools, sources, providers (local only by default) and views a skill may use, and `evals/` holds its cases. `bun run skills:check` and `bun test` validate every skill and run its cases against a scripted model, so a failing case fails CI. A skill cannot widen the data-mode policy. `skills/sleep` is the first. See `docs/skills.md`.
- Charts in answers: the model calls `show_view` with a measure (a LOINC code with a synthetic subject, or a wearable key such as `sleep.score`) and a window; the server reads the rows under the turn's scope, audits the read, and streams a `data-view` part drawn inline in the answer. The model never writes a point, a window with no readings says so instead of drawing, and a reloaded thread draws the same chart from its stored tool parts.
- `/sleep` runs from the chat (#42). The `/` palette lists every skill that validates and passes its cases under "Skills", with what it reads and the tools it may call. A prompt sent as `/sleep last 30 nights` runs under the skill: only its tools (within the user's sources and the data-mode policy), only its providers (another provider gets a sentence saying why it did not run), only its view kinds, and its instructions in the system prompt. The run is audited as `skill.sleep`, the response document carries `skill`, and the prompt shows a `/sleep` chip, also after a reload. `/sleep` charts a wearable's sleep key in personal mode, or a named synthetic subject's sleep duration (LOINC 93832-4) with `baseline_deviation`.
- `training:batches --skip-rejected` continues past bundles the importer rejects, lists them per batch, and still stops above a 1% rejection share.

### Changed

- The synthetic cohort explorer moved into Customize · Data (`/customize/data/cohort`, with Subjects and Training data), so data has one home: your imports and the open datasets side by side. The sidebar's Data item is gone and Digital Twin sits above Customize; `/data/...` redirects to the same view with its query.
- A quieter shell (#165): the header bar is gone and each page's own heading leads. On wide screens the sidebar is either pinned beside the page or tucked behind a button at the top left; pointing at the button or the left edge shows it over the page, moving away hides it, and a click (or Ctrl+.) pins it. The choice is a cookie, so the page renders the right layout without a jump. A saved thread keeps its title and Copy link in a slim row; narrow screens keep the menu dialog.
- Chat on a local Ollama asks for a 16k context (#149). Ollama's 4096-token default cut the tool definitions off every prompt, so `qwen3:4b` wrote tool calls as text. Chat now uses Ollama's native `/api/chat` with `num_ctx` from `OLLAMA_NUM_CTX` (default 16384, at least 8192) and thinking off; the Ollama service needs no change. `bun run doctor` and `setup:local` print the context chat asks for and what each loaded model runs at, `bun run prompt:size --ollama <model>` measures the prompt and tools per data mode and skill, and a test fails when a first turn leaves less than 4,096 tokens free.
- The Ark flow targets Ark CLI 0.5.0 and ArkOS 0.13.1 (#117). The adapter runs `ark run` (`ark app run` is gone), reads the 0.5.0 run, status, doctor and error documents, and names firmware too old, an undelivered approval, an Ark refusal and a failed app. `rsid-genotypes` 0.2.0 prints a TOML `manifest = 1` with the eleven sites as optional grants and `not granted` for a site that is not mounted. The genome card lists both phone steps (approve the run in 5 minutes, release the report in 10), and the report stores the build `data list` names for small variants.
- Tool calls show as folded cards above each answer instead of a one-line status (#39): the call in plain words, its measure, window or subject, running, done, refused or failed, and the rows it read. Expanding a card lists its arguments; tool outputs never show. A reloaded thread shows the same cards, and the "Thinking…" line stays while the model works.
- Evaluation items are spread across subjects: an item that needs another subject, or shares one with more than 3 items, goes to the qualifying subject with the fewest items (ties to the lowest `subject_ref`), so no subject answers more than 3 items (16 before). `bun run eval:spread-subjects` applies the rule from the warehouse; 30 items moved and the answer key was rebuilt from the same cohort (`f4941fab…`), so results scored against the earlier key do not compare item by item.
- `bun run setup:local` downloads the evaluation cohort's pinned files from the `eval-cohort-v1` release (SHA-256 pinned) instead of generating them, because Synthea gives other last digits on Apple Silicon than on x86_64 (#100). `--generate-cohort` still generates locally, and a mismatch on arm64 is reported as a platform difference with the download as the fix.
- Models get slimmer query-tool definitions: no regex patterns or formats, window bounds as plain strings. With the Qwen3 chat template the nine tools take about 2,200 tokens instead of 12,000 in chat and 8,600 in the training data; the server still validates every call as strictly as before, and the MCP manifest is unchanged.
- Repository admins can bypass the `main` rules only through a pull request; nobody pushes to `main` directly.
- Personal data reaches Exoscale only with `EXOSCALE_PERSONAL_DATA=consented-pilot`, each such request is audited, and Infomaniak is synthetic-only.

### Removed

- The schematic four-chamber heart panel beside the live twin (#53): it looked crude and could not be closed. Live vitals still pulse the atlas heart.

### Fixed

- `bun run setup:local` no longer leaves the evaluation cohort three subjects short after the trimmed fixtures were loaded (#96). All three open-twin fixture patients are people of `synthea-v4-seed42`, so loading or reloading that cohort now first deletes `open-twin-synthea-trimmed-3` in one transaction; the checklist note says so. The cohort's 37 subject ids are committed in `scripts/setup/eval-cohort-subjects.ts`, and a test lists which fixtures overlap.
- A turn refused before any model runs (the data-mode policy, a skill's provider or source rule, a skill the server does not offer) is stored as `REFUSED` with its refusal sentence instead of staying `STREAMING` (#99). A reload shows the refusal and does not ask the model again. A data-mode refusal now reads "This model provider may not receive personal data or wearable context, so this model did not run." in the column, live and after a reload. Migration `20261027120000_model_response_refused` adds the enum value.
- The evaluation cohort and its answer key can be regenerated: `synthea-v4-seed42` was generated again with fixed dates (37 bundles, checksum `f4941fab…`, the same under another time zone) and the key rebuilt from it. The key records the dates and checksum, and the tests check them. 13 items got another subject by the rule in `docs/evaluation/question-set.md`, so results scored against the old key do not compare with new ones.
- The evaluation's hallucination scorer fails an answer that reports a measure with another code's value (skin temperature from systolic blood pressure, eGFR from HbA1c) or with a value from outside the asked years, and names the code it came from. A LOINC code at a sentence end is no longer read as a stated number.

### Security

- A thread where `genome_report` or `dna_ask` ran stays on local models (#151). Before, switching to a hosted provider (the consented Exoscale pilot included) and writing on in that thread sent the earlier genome turns with the history. Now every later turn on a model other than Ollama on loopback is refused before any history is sent, stored as `REFUSED` with "This thread used your genome report, so it only runs on local models.", and audited as `genome.thread.refused` (provider and a hash of the thread id). A second check refuses again right before the history reaches a model. `permitGenomeThreadExport` is the same rule for `/report` (#44) to use. `docs/genome.md` rule 6 now says per thread, not only per question.
- `next` and `eslint-config-next` 16.2.12 → 16.4.1, and `zod` 4.4.3 → 4.6.6, for published security advisories; an `overrides` entry keeps every transitive zod on 4.6.6. Query-tool window bounds still accept a UTC datetime without seconds.

## [0.1.0] - 2026-10-25

First public release.

### Added

- Chat over coded health data, with up to three open models answering side by side, each
  with its reasoning, cited values and uncertainty.
- Closed, audited query tools over coded FHIR R4 observations: latest value, trend,
  baseline deviation, coverage and window comparison.
- Digital Twin: a 3D body with reference anatomy, live vitals and biomarkers by organ
  system.
- Data explorer for synthetic cohorts and the training conversations made from them.
- First-run flow for roles, data sources, knowledge sources and data residency.
- Connectors for Oura, Whoop, Google Health and BodyLoop body scans.
- Evaluation harness with 81 questions over a synthetic cohort, and tooling to build
  tool-use training data from Synthea cohorts.
