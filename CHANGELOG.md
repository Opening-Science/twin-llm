### Added

- The second rater rates the v1h review sample (#413). `/lab/rate?set=v1h` shows each rater only the stratified sample of `docs/evaluation/question-set.md`, "Human review": from each run every S5 and S6 line and, per scenario of S1 to S4, the four lines with the lowest sha256 of `v1h-review.v1`, run id, item id and repeat (29 of 44 lines in a whole run). The sample rests on the run files alone, so both raters rate the same lines; each sees them in their own salted order, the automatic score plays no part in drawing them, and the page still gets no run, item, scenario or score. `bun run eval:agreement` lists the sampled lines with their scenario and correctness outcome, a count per scenario and outcome, and computes kappa on the sample; `--all` (and `&all=1` in the view) keeps every line for a second pass. Pure and tested (`features/lab/rater-sample.ts`). hb is unchanged. Synthetic data only.
- GBD location profiles rank causes within one level of the GBD cause hierarchy (#409). Top causes of DALYs and deaths compare only level 2 causes by default (such as cardiovascular diseases and neoplasms), so a parent no longer outranks its own children; causes at other levels are left out and counted in the note, and a cause whose level is not known is named in the note and never ranked. Levels come from a new cause table (`packages/gbd-local/cause-table.ts`, 395 causes: ids, parents, levels and names, no estimates) built by `scripts/gbd/build-cause-table.ts` from `cause.py` of IHME's public, BSD-3-Clause `vivarium-gbd-mapping` package (GBD 2023) at a pinned commit. See `docs/gbd.md`, "Cause levels". Tests use made-up values.
- Maps zoom to the region of the places shown (#408). A map of countries with a value that lie in one part of the world fits their box with a margin and is centred on their own longitude, so Switzerland and its neighbours fill the map; places spread over more than half the globe's longitude, or a box covering half the world, stay a world map. The view counts a country's land near its largest piece and sizeable land not too far from it, so France's overseas regions, Hawaii or the Canaries do not stretch a map of Europe or North America. Places either side of 180 (Fiji, Russia, Pacific islands) make one view across it, and rings that would cross the map's new edge are left out. The narrowest view is 12 degrees of longitude, so Malta or San Marino alone show with their surroundings. Pure (`infrastructure/charts/choropleth/fit-view.ts`), with tests on the committed Natural Earth boundaries. State maps of one country are unchanged.
- The second rater rates the held-out set v1h (#304). `/lab/rate?set=v1h` (tabs switch between hb and v1h; Lab, "Second rating", links both) reads the v1h runs on this machine with `evaluation/questions.v1h.v1.json` and its key, on a rubric of its own, `second-rater.v1h.v1`: the same five labels and pass line as hb, with anchors for data items, decline and refusal items, and items without a keyed reference (S3 guideline and S4 GBD lookups, rated on the item's note). Where an item has no keyed value the view says whether it should be declined or is a lookup. The set travels through the page, the save and export actions and the client; the rubric version names the ratings file's `rubric` and the order seed, and v1h salts live apart in `evaluation/rater-sets/v1h/<pseudonym>.json`, so hb salts, answer ids, files and order are unchanged. `bun run eval:agreement` reports one table per question set, never pooling hb and v1h, leaves out a ratings file whose rubric is not its run's set's, and maps `--ids` with that set's salt. The protocol's stratified sample is not drawn in the view yet. See `docs/evaluation/second-rater.md`. Synthetic data only.
- GBD location and cause profiles (#403). The `/profile` skill (`skills/profile`) asks for one place ("/profile Switzerland") or one cause, like IHME's GBD profiles, and the new tool `gbd_profile` runs a fixed sequence of `gbd_estimate` calls, each audited as `gbd_estimate`. A location profile reads HALE and life expectancy at birth for the place, its parent region and the world over the profile years (1990 to 2023), a trend when more than one year is imported, the top causes of DALYs (age-standardised rates, one call per imported cause, All causes left out), and HALE for the units inside the place or else its neighbours for the map; deaths by cause only with `deaths: true`. A cause profile reads the world's DALY rate over the years (age-standardised, else all ages), every imported country in the latest year (a ranked top 10 and a world map), and females and males; deaths only when asked. The sections are assembled by pure code (`packages/gbd-local/profile.ts`) and drawn as a sections table, one table per section with rows (numbered for a ranking), and a choropleth with its own `gbd_profile.map` audit row (`features/chat/gbd-profile-views.ts`); a section whose estimates are not imported says so in one plain sentence. Several views now stream from one tool output (`toChatViews`). The tool is built only for a skill turn that lists it, so other turns' prompts are unchanged. Population estimates only. Tests use made-up values; no IHME data is in the repository.
- The free text check of outgoing model requests also searches lab values, coded values, clinical records and twin note lines (#346). Opened once per model call, as none of these stores keeps a keyed hash of a value: a stored reading's number followed by its own unit (`195 mg/dL`), a reading's code with its own number within 80 characters, a Condition or MedicationRequest by its code or a name of 24 characters or more, and a twin note title or line of 24 characters or more, each as a whole token or phrase. A stored value that also stands in the person's own messages of the turn is not counted, since they sent it themselves; `resolveLanguageModel` takes those messages as `typed`. The four kinds are recorded and never block: they are values, not identifiers, so option C (#356) stays with rsIDs and genome sites. The 500 lookup cap is unchanged; the new kinds make no lookups. Wearable numbers are not searched (a bare number matches too much ordinary text). Customize · Privacy and `docs/privacy-design.md` 2.5 list the kinds. Synthetic test data only.

- A code arm for the eval harness (#303): `bun run eval -- --arm code` gives the model one tool, `run_python`, and a JSON file of the record of the subject the question names (chosen as the fair arm chooses it, never from the key: every numeric observation, condition and medication request). The prompt lists the file's layout and its codes with counts and dates, no readings. Each program runs in a sandbox (`scripts/evaluation/code-sandbox.ts`): bubblewrap with every namespace unshared and no network, an empty read-only root holding only the interpreter, its libraries and the input file, a 16 MiB tmpfs to write, an empty environment, and a systemd user scope plus `prlimit` for memory, tasks, CPU and file size, with a 15 s wall clock and capped output. An item may run 3 programs (2 retries); each run's code, outcome and capped stdout and stderr go in the results line, and `meta.json` records the sandbox, its limits and the run counts. Before any item, the harness runs 11 escape probes (network, host files, writes, environment, namespaces, an infinite loop, a fork bomb, memory, output, file size) and refuses to start unless all are contained; `code-sandbox.escape.test.ts` runs them in `bun test`. Scored by the same scorers; call accuracy is n/a. See `docs/evaluation/harness.md`, "The code arm".

- How much AF signal survives from beats to daily summaries (#290). `bun run rhythm-bench:resolution -- --out .rhythm-bench/resolution-<run> [--subjects N] [--afdb <dir>] [--ltafdb <dir>]` (`scripts/rhythm-bench/resolution/`) builds 24 h days from 144 ten-minute `packages/rhythm-sim` recordings (read only) with an assumed circadian swing, activity bouts and ectopy, for subjects with baseline, sinus and AF days at 2, 10, 30 and 60 % burden, and scores each day at beat level, 30 s, 5 min, hourly and daily with the pure ladder in `aggregate.ts` (epoch mean heart rate and RMSSD, and the v3 daily heart rate, night resting heart rate and night RMSSD computed from the beats). AUROC of AF days against sinus days with 95 % bootstrap intervals over subjects, as raw scores and as change from the subject's baseline, and of AF hours against AF-free hours on simulated days and on the MIT-BIH AF and Long-Term AF databases (read in place, bootstrap over records). Results in `docs/research/af-resolution-2026-10.md`: on clean beats every level that keeps beat-to-beat irregularity separates AF days down to 2 % burden (0.98 to 1.00), while the daily values do not (night RMSSD 0.51 at 2 %, 0.79 at 60 %); 1 % missed and spurious beats spoil RMSSD over 5 min and longer epochs; real hours separate less than simulated ones at every level of irregularity. The v3 AF effects are stronger than the beats give at low burden. The database readers moved from the benchmark's CLI to `scripts/rhythm-bench/read-database.ts`. Not done: an open PPG check and a PaPaGei baseline. Simulated data and open databases only; methods, not people.
- Held-out S1 to S6 items (#304). `evaluation/questions.v1h.v1.json` holds 32 items, `Q-S1-H01` to `Q-S6-H05`, drawn on the evaluation cohort by a seeded rule (`scripts/evaluation/heldout-v1h.ts`, seed 3040) that was committed with its templates and subject table before any item was generated or any tool called. - Rhythm simulator: a second AF mode with short-range dependence (#297). `afDependence: "short_range"` makes ln RR a Gaussian AR(1) with lag-1 coefficient 0.055, fitted to the lag-1 autocorrelation of ln RR in all-AFIB windows of the MIT-BIH AF Database (0.043 per record, 0.054 pooled), with the same log-normal intervals as before. `independent` stays the default, so existing recordings and snapshots are unchanged. `bun run rhythm-bench -- --af-dependence short_range` runs the benchmark with it; every run now reports lag 1 to 3 autocorrelation of ln RR for simulated and real AF windows and a `lag1_log_rr` row in the simulated-against-real tables. Rerun on both databases: simulated sensitivity 0.973 to 0.960, specificity unchanged, database results unchanged (`docs/research/rhythm-bench-2026-10.md`). A statistical model, not a physiological one.
- OAuth and BodyLoop tokens under the vault key (#341). In personal mode the Oura, Whoop and Google Health access and refresh tokens and the BodyLoop API token and upload secret are sealed with the person's vault key (AES-256-GCM under the `field` subkey of #141, with table, column and row id as additional data) on top of their `*_TOKEN_ENCRYPTION_KEY` ciphertext, so a copied row opens with neither key alone. The four `*_connections` tables are in `infrastructure/personal-columns.ts`, so `bun run vault:migrate` seals tokens stored before (run it once more on an existing personal install), `bun run vault:rotate` moves them to a new key, and the doctor and the Lab count any left plain. Nothing opens or stores a token while the owner's vault is locked: an OAuth return then exchanges nothing, writes a `vault.locked.skip.connect-<provider>` audit row and shows "Your data is locked, so Oura was not linked. Unlock it, then link Oura again." with a Try again link (new `locked` outcome); a BodyLoop scanner upload answers 423 without opening its secret and writes `vault.locked.skip.bodyloop-upload` at most once per connection per 10 minutes (an unknown connection id gets 401 and no row), as a scheduled task skips (#54). Before, an OAuth return while locked stored the tokens and skipped only the first sync. Synthetic installs are unchanged. See `docs/privacy-design.md` 2.2 and 2.3 and `docs/runbook.md`, "Encryption at rest".
- Salted answer ids for the second rater (#355). When a rater's set starts, the server makes a 32-byte random salt and keeps it in `evaluation/rater-sets/<pseudonym>.json` (gitignored), never in the page or the export. Answer ids are now HMAC-SHA256 of run, item and repeat keyed by that salt (first 16 hex characters), and the order is an HMAC under the same salt, so knowing the run ids no longer lets a rater recompute which model gave an answer. `bun run eval:agreement -- --ids <run-id> …` maps each rater's ids back to run, item and repeat. Ratings files are unchanged; ratings made before this keep working and get a new salt, new ids and a new order on the next load. `docs/evaluation/second-rater.md` has a Blinding section for the methods.
- The disclosure ledger checks outgoing free text for stored values (#346). Before each request to a hosted model is recorded, its text (the person's words, earlier answers, tool results) is searched for values stored on this machine: rsIDs and genome sites of the person's imported VCFs, looked up through their keyed hashes so no variant is opened, and, as whole words, the file names of their imports, body scan labels other than their own and a distinctive account id. The row stores `free_text_checked = true` and the new `free_text_matches` column (migration `20261031170000_disclosure_free_text`): kinds and counts only, never a value; the paired audit row carries the same list, and the chain covers the column only when it is set, so earlier rows keep their hashes. Customize · Privacy shows "Free text" on each event (kinds and counts, "no stored values found" or "not checked"). A match is recorded and does not stop the send; whether it should is open. A body that cannot be read up front, or a check that fails while the vault is locked, is recorded as not checked. The matcher is pure (`infrastructure/free-text-check.ts`). Limits: approximate; a value written another way is missed, lab values, clinical records, twin notes and wearable numbers are not searched, and exports, embeddings and live lookups are not checked yet. Synthetic test data only.
- Live lookups accept public topic names with digits (#349). The PubMed search-term check now lets through a short reviewed list of public disease and topic names that contain digits, such as type 2 diabetes, COVID-19, long QT syndrome type 1, H1N1, vitamin B12 and SGLT2 inhibitors (`packages/live-sources/topic-allowlist.ts`, 42 phrases from 28 MeSH records, each citing its MeSH id). A phrase is matched whole and in any case and removed before the digit rule runs, so any other digit is still refused ("type 2 diabetes 140" is refused), and a year is never allowed. The refusal sentence and the `pubmed_search` description say so.
- Second-rater scoring for the heart-brain set (#351). Lab, "Second rating" (`/lab/rate`), shows the answers of every hb run on this machine one at a time, pooled and in an order fixed by the rater's pseudonym, with the question, the answer key's reference and the reply, and without the run, model or automatic score. The ui-kit `Rating` takes a level from 1 (wrong or invented) to 5 (right and grounded), each with a written anchor (`docs/evaluation/second-rater.md`). Ratings are saved on a local install only, to `evaluation/runs/<run>/ratings/<pseudonym>.json`, and never sent anywhere; reopening resumes at the first unrated answer, and export (once all are rated) gives one JSON document. `bun run eval:agreement -- <run-id> …` prints Cohen's kappa with a 95 % interval (Fleiss, Cohen and Everitt standard error) for each rater against the correctness scorer and between raters; the test reproduces Cohen's worked example. Synthetic data only.
- Press and hold for privacy actions that cannot be undone (#350). Withdrawing a learning consent on Customize · Privacy ("Hold to withdraw consent") and setting a new passphrase with the recovery code on the unlock screen ("Hold to replace passphrase and recovery code") now need a press and hold of 1.5 s with a pointer, Space or Enter; letting go early cancels and submits nothing. New `HoldToSubmit` in the ui-kit wraps `HoldToConfirm` for a form: a completed hold calls `requestSubmit` once, so the server action or submit handler runs as before, any other submission of that form (Enter in a field) is stopped, and a refused submission leaves the button ready again. `HoldToConfirm` now keeps its timing in `hold-timer.ts` (tested with a fake clock: one fire at the end, none after an early release) and, under reduced motion, shows a countdown in the label ("Keep holding: 2") instead of a stepped fill. Deleting a thread or an imported dataset keeps its Undo window. Lock, unlock, first setup and Grant are unchanged, since each can be reversed. See `docs/coding-standards.md`, "Interaction patterns".
- Live PubMed and Ensembl lookups, off by default (#6).
